## 2. PicaComic：统一阅读层，分来源网络

- `ReadingData` 为在线和本地提供同一加载入口；具体来源负责章节图片列表、图片请求和缓存键，阅读视图不需要知道全部站点细节。证据 PICA-READ。
- picacg 登录 `auth/sign-in` 取得用户 token；请求另有时间、nonce 和 HMAC 签名。用户 token 与签名不是同一个东西。证据 PICA-PICA / PICA-SIGN。
- EH/EX 使用 Cookie，作品链接还包含 gallery token；图片页解析与画廊详情是不同请求。证据 PICA-EH。
- JM 的 API 返回解码与图片分块重组在不同层；正文图在显示前被还原。证据 PICA-JM / PICA-IMAGE。
- Hitomi 从 hash 与动态 gg.js 规则推导图片 URL，不能把某次得到的 CDN 前缀永久写死。证据 PICA-HITOMI。
- htcomic 在此项目里是绅士漫画/wnacg 这一组实现，网页含 `photos-*`、`users-check_login.html` 等路由；不是所有名字带 hcomic 的网站。证据 PICA-HT。

视觉证据 PICA-UI：Material 3、由种子色生成主题、明暗模式；阅读证据 PICA-VIEW：PhotoViewGallery 与连续列表组合。因此 PiComic 的 Compose + 图片库组合在结构上合理。

## 3. Hazuki：主程序和抓取规则分离

HAZ-CATALOG / HAZ-CONFIG / HAZ-ASSEMBLY 显示源目录与脚本来自 Venera configs；配置下载可选择 GitHub raw、jsDelivr、镜像。**这些是脚本分发地址，并非漫画 API 地址**，PiComic 不应把它们当内容中转服务器。

HAZ-SESSION 按 sourceKey 分别保存 account、token、cookies，使用 flutter_secure_storage。HAZ-RELOGIN 将会话恢复从具体收藏等业务中分离，并存在登录失效后恢复再重试的路径。PiComic 借鉴职责划分，但用明确错误类型代替任意字符串包含“401”的判断，并增加 single-flight、代际检查和次数上限。

追读的 Venera `jm.js`（VEN-JM）包含：接口域名候选、发现文件、内容 API 与图片分流地址分离、请求时间签名、响应解码。`picacg.js`（VEN-PICA）包含：用户密码登录、保存用户 token、配置 base_url、按请求生成签名。它们可作为协议对照，不能直接在不支持插件的产品里悄悄执行。

## 4. jm-mobile：原生 Kotlin 路径最接近

JM-HTTP / JM-TOKEN / JM-URL 展示 OkHttp 拦截器串联：初始化、动态地址、协议签名、响应解码；Retrofit 使用占位 baseUrl，实际地址由配置替换。

JM-LOGIN 通过 multipart 向 `login` 发送用户名密码；JM-COOKIE 存储并恢复 Cookie；JM-USER 在启动时存在用已保存账号密码自动登录的路径。PiComic 将“记住密码”设为明确选项，不因参考项目保存了密码就默认照做。

JM-API / JM-API-VM 从独立地址拉取 API 清单并加入本地列表。其名字包含 Proxy，但该代码证明的是**地址清单服务**，不是 Android 的 HTTP/SOCKS 代理设置。

需要独立处理的源码细节：

- JM-CONSTANT 的时间戳为顶层值，PiComic 应为每次请求生成时间并让解码使用同次请求元数据。
- JM-HTTP 的 CookieJar 加载路径直接返回 cookieList；PiComic 必须匹配 host/path/secure/expiry，不能照搬到六来源环境。
- JM-DECODE / JM-IMAGE 表明图片页解析参数与图像重排相关，处理参数要跟随章节和页面，不能用全局猜测值。

这些是设计取舍，不是对竞品的全面安全审计。

## 5. Breeze：真正的抓取代码在插件仓库

BREEZE-INDEX 追踪到独立 JM、picacg、EH、NH、绅士漫画插件。本轮读取了这些仓库；其具体快照也写入证据索引。未从索引确认 Hitomi 实现，Hitomi 以 PicaComic/Venera 为参考。

### JM 的协议差异

BZ-JM-CLIENT 会从解码结果提取 `jwttoken`，后续请求附加 `Authorization: Bearer ...`；另有 `token`/`tokenparam` 请求头。与 jm-mobile/Venera 的签名输入、版本、会话路径存在差异。**不能推断“JM 只靠 Cookie”，也不能把几个项目的常量混在一起。** P0 联调应先确认可用服务族，再固定一套协议 profile。

### picacg

BZ-PICA-LOGIN / BZ-PICA-CLIENT 展示密码登录取得 authorization token，以及逐请求签名。平台未在这些路径中提供通用 OAuth refresh_token。PiComic 会话恢复应写成验证/重新登录，而非虚构统一刷新接口。

### EH/EX

BZ-EH-SESSION 分开处理论坛 Cookie、`ipb_member_id`、`ipb_pass_hash` 与 `igneous`，包括受限重定向和 EX 检查。BZ-EH-ROUTE 存在 EX 失败后 EH 路由处理。PiComic 将“可登录”和“可访问 EX”分开显示，切 EH 由用户明确选择，不静默换站。

### NH 的新 API 路径

BZ-NH 使用 `https://nhentai.net/api/v2`，API Key 以 `Authorization: Key ...` 发送，并有 Key 校验及能力限制。VEN-NH 除 Key 外还处理网页登录 Cookie 中的访问 token，用 `Authorization: User ...`，并保留网页兼容路径。

这与旧 PicaComic 的 HTML 抽取方式不同。PiComic 首先验证近期 API v2，再根据实际能力决定网页登录与网页读取的保留范围。源码中的 API Key 不是所有用户天然拥有的固定密钥，也不是可写入 APK 的公共常量。

### 绅士漫画 / htcomic

BZ-HT 包含发布页发现、候选站点缓存、登录路由与 Cookie；与 PICA-HT 的站点家族相符。候选地址依然要验证结构与信任范围，不能把发布页所有链接都当作安全 API。

## 6. 转化为 PiComic 的决策

| 决策 | 依据 | 落点 |
|---|---|---|
| 固定 Kotlin 适配器 | 六来源明确，无用户扩展需求 | SourceRegistry 静态注册 |
| Token/签名/Cookie 分类型 | JM/Pica/NH 三种路径不同 | SessionStore + RequestSigner |
| API 与图片地址分开 | JM 分流、Hitomi 动态 CDN | EndpointRegistry |
| WebView 与 API 显式桥接 | EH/NH 网页会话 | CookieBridge + 路由一致性 |
| 平台错误与网络错误分开 | 未授权、EX 权限、图片额度 | SourceFailure 类型 |
| 规则漂移可定位 | 原版归档、近期插件协议变化 | 来源 profile/version + 夹具测试 |

## 连续阅读章末补充核对

PicaComic 的 `buildType4()` 按 `logic.urls.length` 构造连续图片列表，没有另外插入固定高度的章末项目；阅读工具栏通过 Stack 覆盖在画面上，章末使用 `Scaffold.floatingActionButton`。上拉时以位移的三分之一累计悬浮按钮填充进度，松手达到阈值后换章。以上是源码核对，未运行其 Android App 对比实机动画。
